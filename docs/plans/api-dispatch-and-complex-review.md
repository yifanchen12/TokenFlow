# 北邮 API 调度与复杂任务复核升级

状态：2026-10-23 用户明确批准实施并启用，确认连接为“北邮 DSv4 API”。用户优先要求解决“有效参考增加，但正确候选通过仍为 10/60”，并提出复杂任务由北邮 API 选择后交给 Harness 执行。

## 需求理解与完成标准

让小模型退出复杂任务的执行与最终裁决。确定性解析、查表与已有本地程序继续使用；北邮 API 负责分工，从已配置且满足当前任务执行模式的 Harness 中选择。复杂结果使用独立上下文的 Harness 参考核对，原答案仍保留。

本轮验收看正确候选通过、错误放行与完整任务正确完成，不把路由成功或协议合规当作任务正确。交付包括源码、真实连接验证、独立 EXE 和结果报告；按本会话已有要求提交 GitHub。旧产物与数据保留。

## 根因证据

- 原生固定候选回放有 24 个正确候选，通过 10 个、误拦截 14 个；36 个错误候选均未通过。
- 14 个误拦截中，7 个参考本身错误：流水版本选择 5、依赖排期 1、门槛政策 1。其余 7 个参考无效：单位换算 4、排期 1、跨表 1、选优 1。
- 已观察到正确参考因多列引文或字符串编号计算被拒绝，也有算式与参考字段确实冲突。不能将这些情形统一当作正确、统一忽略计算，或直接取消复核。
- 桌面实际保存的北邮连接是 `imported-dsh` / 北邮 DSv4 API，协议 openai、模型 `deepseek-v4-flash`；已保存密钥。Codex 执行器绑定为原生 `gpt-6-astra`。前轮评测使用 `gpt-6-luna`，两者必须在报告中区分。
- 当前默认运行环境的配置路径不同于桌面目录；已用 SQLite 只读连接找到桌面配置，没有读取或输出密钥值。

## 复用调查

- `task_orchestrator.py` 已有 planner、执行步骤、独立复核、预算、取消、候选保留与配置快照；扩展现有分工计划，不新增一套调度器。
- `runtime_config.py` 已有提供商连接、角色模型、Harness 绑定及协议检查；复用 planner 作为 API 调度角色，绑定模型不由提示词随意改写。
- `tokenflow.py/detect_harnesses、execute_configured_harness` 已支持实际执行器目录和连接绑定。纯文本隔离目前只支持 Codex；首版普通分析任务可选的是当前隔离模式就绪的 Codex，不能将 Claude/DSH 标为已经支持同等文本隔离。
- `answer_checks.py` 已有严格数值/JSON、引文和字段计算检查；本轮保留其核心通过标准。
- `ui_page.py` 已有角色设置、分工预检、执行阶段与记录视图，增加调度开关和选择说明即可。
- `test_collaboration.py`、`test_orchestration.py`、`test_acceptance.py`、`test_recovery.py`、`test_native_text.py`、`scripts/test_ui.js` 覆盖相关行为；复用现有生成题、独立标签校验和评分工具。未发现需要新增依赖的缺口。

## 能力与文件边界

1. API 选路：`task_orchestrator.py` 复用 planner 调用，只生成复杂度、目标、简短理由与本地操作类型，由程序构造一个现有执行步骤；`runtime_config.py` 保存可选 API 调度开关，复用 planner 连接与现有 Harness 绑定。
2. 执行与复核升级：`task_orchestrator.py` 校验复杂计划，复杂路线禁止 `local_model` 步骤，最终执行和独立复核均使用所选 Harness 的已绑定模型。确定性本地程序不受此限制。
3. 展示与回执：`ui_page.py` 在已有设置和进度中说明调度 API、选择理由、实际执行器与复核目标；回执区分“API 选择”与实际调用。
4. 验证：扩展受影响的现有测试，新增本轮模型试跑脚本及报告，继续使用原评分与完整用量计量。

重要保持不变：`native_text.py` 的工具禁用与隔离实现、价格和累计节省口径、连接密钥保护、文件任务既有授权、原答案保留、标准答案与评分门槛、个人文档和 `deliverables/`。

## 接口与不变量

- 设置开关 `api_dispatch`：只在端云协同策略下启用，缺省关闭以兼容旧配置。planner 必须绑定已保存的非本机 API；未配置时预检明确提示，不擅自选择其他账户。
- `dispatch selection`：四字段 `complexity=simple|complex|uncertain`、`selected_harness`、`routing_reason`（80字内）、`local_operation=none|summarize|classify|translate|extract`。程序将它组装成现有单步计划，原任务与完整原文交给执行器。uncertain 按 complex 处理，不会用“只输出一个数字”判断任务简单。
- 可选目标来自已安装、已绑定且满足本次任务执行模式的目录；API 不能返回任意模型、端点、命令或未就绪的 Harness。首版分析任务沿用 Codex 现有隔离文本模式。
- complex/uncertain 计划不能包含本地模型步骤；最终答案必须由所选 Harness 输出，复核也不能交回本地小模型或低成本调度 API。simple 只有在实际存在本机模型且步骤属于摘要、分类、翻译或直接提取时才可安排本地模型；复杂度误判仍需实际评测发现，不能称作程序证明。
- 普通分析任务通过现有 `model` 步骤调用选定 `native:<harness>`，保持文本隔离；现有有工具权限的 `harness_step` 仍只用于用户明确要求的文件/工具任务。选路不能把分析任务自动改成工具执行。执行与复核目标在任务快照内确定，不改全局模型绑定。
- 调度阶段只负责分配，不提前生成答案或把猜测结果写入后续指令。执行收到原任务与必要资料，复核收到完整原文和原任务，不收到候选、执行者推理或调度答案。
- 复核仍使用现有独立参考契约与本地检查。候选与参考不一致/参考无效继续保留原答案，不通过降低标准消除误拦截。每次任务只执行一个选定计划，不循环试遍模型挑答案。
- 预算将 API 调度、Harness 执行及最终复核一并纳入现有 max_calls/max_task_tokens；执行前预留复核。超预算、无可用执行器或 API 输出无效时明确失败或待复核，不回退给小模型完成复杂步骤。
- 仅本地策略不调用北邮 API 或 Harness；显式角色策略保留原有行为。取消、恢复与配置快照不得绕过这些约束。
- 默认沿用已发现配置：北邮 `deepseek-v4-flash` 调度、Codex 原生绑定 `gpt-6-astra` 执行复杂任务及独立参考。启用其它 Harness 前按其当前执行模式核查，不扩大工具权限。

## 实施顺序

1. 独立验证可用目标目录、分工计划与复杂路线限制，使用已有回放中真实出现的失败形态；验证 API 伪造目标、复杂任务派给本地、预算不足均在执行前阻止。
2. 组装 API 分配、目标冻结、执行与独立复核；验证候选不泄漏到参考输入、没有自动语义改写、取消/恢复不重复计算旧调用。
3. 接入任务入口、预检及既有设置/进度视图；使用隔离配置跑通，再为桌面现有北邮连接启用此策略，保持密钥和用户模型绑定不变。
4. 按以下停止条件做真实连接试跑、冻结代码后评测，完成打包、报告与 GitHub 提交。

## 验证与停止条件

- 离线自检：相关分工/验收/恢复/隔离测试、`node scripts/test_ui.js`、`python tokenflow.py --self-check`、`python eval_workflow.py --self-check`、`git diff --check`。
- 真实连接先验证 API 可用性及实际模型名；有密钥不等于接口可用。密钥只由原有受保护配置读取到内存，不输出、不写报告、不要求用户发送。
- 真实开发试跑中，DeepSeek V4 调度的默认请求耗满 1536 输出预算；服务内部如何处理推理未被完整观察。仅调度请求采用官方支持的 `thinking.type=disabled` 和 `response_format.type=json_object`；保持原输出上限，不改变其它模型、执行和复核的推理设置。中止的开发试跑及在途未知用量全部保留，新代码按原门槛重新验证。这是接口适配修复，不是重跑相同实现挑分数。依据：https://api-docs.deepseek.com/guides/thinking_mode/ 、https://api-docs.deepseek.com/guides/json_mode/ 。
- 关闭思考后的开发试跑仍出现调度截断，说明让选路 API 输出整份步骤计划增加了不必要的负担。将外部契约精简为上述四个选择字段，输入只提供原任务、原文首行及结构统计，完整数据留给执行/复核。保留两次开发实现的结果、成本和在途未知调用，再用固定门槛验证最终实现；不挑选较高分的试跑作为结论。
- 固定小批：原生回放的 14 个正确但被拦截候选，以及按六类各选 2 个既有真实错误候选，共 26 条。先固定名单，再调用北邮路由与所选 Harness 参考核对；原候选与标签不改。目标是至少 12/14 个正确候选通过、错误候选通过 0/12、复杂执行/复核的本机模型调用为 0。
- 小批未达标则停止扩大调用，记录具体失败；不反复重跑同题挑好结果，不换算为完整任务达标。
- 达标后，用未参与修改的 V4 新数值 60 题（固定种子 202610234、原六类模板）跑实际 API 调度→执行→独立验收完整流程；标准答案仍由独立算法核对。保持 >=90% 等既有质量门槛；新题不是新模板或真实项目，与旧版不同模型、不同样本的数据不作单因素因果比较。
- 同时记录首次答案正确、最终正确完成、错误放行、正确未完成、实际路由、调用、Token 和未知用量；API 与 Harness 模型分别列出，不能把预算额度或未知用量当作实际节省。
- 包装到 `dist/api-dispatch/`，真实 EXE 验证选路、失败保留与关键界面；保留旧 EXE。质量不足仍明确标为评测版。

## 已验证事实与假设

- 已验证事实：上述 14 条逐题分类、已有连接名/保存模型、已安装执行器及当前文本隔离限制。
- 待验证假设：北邮 API 能稳定作出分配，当前绑定的更强复杂执行/复核组合能降低误拦截并提高任务正确完成率。路由本身不能保证答案正确，同一模型的两个独立上下文也不证明语义正确。
- 开放问题：接口实时可用性与本轮实测质量，需真实调用验证；实施后的真实调用、桌面启用、完整验证及剩余限制见 [本轮验证报告](../reports/api-dispatch-2026-10-23.zh-CN.md)。
