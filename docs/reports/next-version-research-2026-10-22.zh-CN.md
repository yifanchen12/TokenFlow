建议先修两处运行一致性问题，再优化验收与端云净收益。当前最主要的已测开销来自复核，而不是规划。下一版沿用已有连接、预算、顺序步骤和工作空间，在这些能力上补证据与稳定性。

## 二、本轮新复现的两处一致性问题

### A. 两个进程共用数据库时，运行记录可能被误判和误删

`runtime_config.py:574`、`:589` 把“运行记录的 PID 与当前进程不同”直接视为中断；`:543` 对运行记录的删除保护也仅覆盖当前 PID。`task_orchestrator.py` 的运行锁只在单个进程内有效。

隔离复现：父进程写入属于自己的合成运行记录，父进程删除该记录被阻止；另一个仍与父进程同时存活的进程读到 `interrupted`，随后能删除同一记录，数据库剩余记录数为 0。实验没有启动模型或删除用户任务。

影响条件是两个服务或工具共用同一配置数据库，例如使用不同端口启动两份服务。这不等于普通的同一服务多标签页问题。

建议先按配置数据库约束服务实例所有权，并让读取、删除和清理共用同一判断。不同 PID 不能单独证明进程已经结束。第二个实例应获得明确的复用或拒绝启动反馈；再考虑断点恢复。

验收：两个进程共用数据库时不能重复启动同一批工作、误标或删除仍运行的任务；真正退出的旧实例仍可被识别为中断；不同数据库的独立实例不互相阻塞。

### B. 修改连接会影响已创建任务的后续调用

`TaskRun.__init__` 保存了 `config_snapshot`，但执行器在 `task_orchestrator.py:389` 等位置重新读取连接。该快照目前没有约束后续调用。

隔离复现：创建任务时连接指向回环端口 9、模型记录为 `fixture-v1`；随后编辑同名连接，改为端口 10、模型记录 `fixture-v2`。模拟执行器实际接收到新地址，并在自动选模时使用 `fixture-v2`。全部网络调用由夹具替代，外部请求为 0。

建议运行中任务使用固定的连接、模型与绑定参数，设置修改用于后续任务；页面明确说明生效范围。密钥继续按现有方式保护，运行快照不把明文密钥写入记录。原生执行器的绑定读取路径也需一并核查，不能只修 API 调用分支。

验收：任务运行期间改连接、模型或 Harness 绑定，不改变已启动任务后续阶段的目标；新任务使用新设置；记录展示的分配与实际调用一致。

### 可信验收的具体方向

- 复用已经可靠的表格查值和统计；增加本地验证能力时先明确支持范围。例如仅对可静态求值、资源有界的简单数值表达式与函数依赖试点，不把任意 Python 执行当作校验器。生成器的标准答案与验证器保持独立，避免只对已见模板有效。
- 自然语言及超出本地验证范围的任务继续核对原文。输出格式正确、引用存在和事实判断正确分开记录；不能把无效 JSON 改写成通过，也不能根据理由中的“正确”二字翻转 verdict。
- 复核输出控制为必要结论和证据，比较适合复核的已有模型／配置，并记录正确通过、错误放行、误拒绝、修正改善和修正退化。缩短提示或换模型的收益都需要重新实测。
- 对资料内干扰指令、缺失条件和应拒答任务另设验证集合。现有正向质量门槛会拒绝任何未完成任务，不能把正确拒答混进去后当作失败，也不能借新集合放宽原有正向门槛。

### 端云评测的具体方向

`evaluate_pipeline` 当前明确限定所有角色使用同一连接、同一模型（`eval_workflow.py:304–342`）。它适合隔离流程影响，但不能直接覆盖真实的本地模型＋复杂执行器组合。

在现有隔离评测中增加三种可比较条件：

1. 单次原文调用，作为成本和延迟的基础参照。
2. 原文执行＋相同标准的验收，比较同等验收要求下的额外开销。
3. 实际端云分配流程，记录每个角色的实际连接位置、模型、输入输出、耗时与失败。

沿用既有每次调用的 `duration_ms`、usage、角色和地点记录生成报告，先补汇总与对照，不另建监控系统。原有同模型模式保留。先用小开发集检验方案，再用未参与调参的样本评测；原有已见 120 题用于回归，另补真正的多步骤任务和拒答集合。真实业务样本补充后单独报告。

准入仍保留原有正确率、分类覆盖、事实保留、输入与总 Token 节省门槛。新增效率结果按单次、同等验收和端云三种口径分别呈现，不将估算冒充账单，也不以取消原文验收换取表面收益。

## 四、建议实施顺序

1. **先做运行一致性**：把两处已复现问题补成定向检查，再修共享判断与运行参数生效范围。
2. **再做验证能力和评测汇总**：先验证独立的本地校验及计量，再与已有执行／复核流程组装，最后接入任务入口。
3. **以数据决定分配调整**：新增有多步依赖的端云对照，再决定辅助摘要与规划何时值得调用。
4. **接入恢复和过程交付体验**：建立在稳定的任务所有权、输入和配置行为上，继续使用已有预算与只读权限。

首批建议包含 P0 和 P1 三行；P2 作为下一批。产品实施后的常规检查仍是主程序自检、评测自检、UI 回归、桌面／手机操作、EXE 构建与冒烟。本轮未改产品实现，因此没有把历史的自检、模型或 EXE 成绩说成今天的新验证。
